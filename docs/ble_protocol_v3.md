# Activity Tracker BLE dataset protocol v3

> Historical contract. The current paired firmware and Android implementation
> uses [protocol v4](ble_protocol_v4.md).

This document is the source of truth for dataset recording and CSV transfer.
The Android application and firmware are upgraded together; v1 and v2 are not
wire-compatible with v3.

## GATT service

The existing service and characteristic UUIDs remain stable:

| Name | UUID suffix | Properties |
| --- | --- | --- |
| service | `0000` | - |
| current activity | `0001` | read, notify |
| activity summary | `0002` | read, notify |
| battery | `0003` | read, notify |
| command | `0004` | write with response |
| control response | `0005` | read, indicate |
| file data | `0006` | notify |

All UUIDs use the base `7b7d0000-8f7a-4f6a-9f4f-1d2c3b4a5000`.

The client requests MTU 247 for throughput, but the protocol must remain
correct at the default MTU 23. Control records may span multiple GATT writes or
indications. Both peers reassemble bytes until a newline (`\n`) is received.
A control record is UTF-8, contains no embedded newline, and is limited to 256
bytes including the terminator.

## Common fields

- `request_id` is an unsigned 32-bit decimal integer in the range
  `1..4294967295`, chosen by Android and present in every command and its
  responses. Value `0` is reserved for asynchronous firmware events and is
  rejected in commands.
- `label` is exactly one of `walking`, `running`, `cycling`, `sitting`, or
  `lying`.
- `name` is generated by firmware and must match
  `[a-z0-9_]+_[0-9]+\.csv`; path separators are forbidden.
- `size` and `offset` are unsigned 32-bit decimal byte counts.
- `crc32` is the IEEE CRC-32 of the exact CSV bytes, encoded as eight uppercase
  hexadecimal characters.
- A successful one-line response starts with `ok`; a failure starts with
  `error,<request_id>,<code>`.

## Commands and responses

```text
hello,<request_id>
ok,<request_id>,hello,3,recording;catalog;download;resume;crc32

status,<request_id>
status,<request_id>,idle,<last_name|none>,<last_size>,<last_crc32|none>,<free_bytes>
status,<request_id>,recording,<label>,<active_name>,<elapsed_ms>,<bytes_written>,<free_bytes>
status,<request_id>,fault,<error_code>,<active_name|none>,<free_bytes>

record_start,<request_id>,<label>
ok,<request_id>,recording_started,<label>,<name>
ok,<request_id>,already_recording,<label>,<name>

record_stop,<request_id>
ok,<request_id>,recording_stopped,<name>,<size>,<crc32>
ok,<request_id>,already_stopped,<name|none>,<size>,<crc32|none>

list,<request_id>
file,<request_id>,<name>,<size>,<crc32|none>,<complete|incomplete>
list_end,<request_id>,<count>

download,<request_id>,<name>,<offset>
download_begin,<request_id>,<name>,<size>,<offset>,<crc32>
download_end,<request_id>,<name>,<size>,<crc32>

cancel,<request_id>
ok,<request_id>,cancelled

delete,<request_id>,<name>,<size>,<crc32>
ok,<request_id>,deleted,<name>
ok,<request_id>,already_deleted,<name>

error,0,<fault_code>
```

`error,0,<fault_code>` is an unsolicited notification that recording entered
`Fault` because of a storage/write/finalization problem. Firmware retries this
event when the indication channel is busy and after reconnect. Android treats
it as a collection fault even when no command transaction is active; `status`
remains authoritative after reconnect.

`record_start` is atomic: there is no separate BLE command that mutates a
persisted label. Repeating it while the same label is already being recorded
returns the active session. A different label returns
`error,<request_id>,already_recording`.

`record_stop` is recoverable after a lost response: while the firmware remains
powered it returns metadata for the most recently closed session. After a
disconnect, Android always reconciles with `status` before allowing another
mutation.

While recording, `hello` remains available for reconnect handshakes, `status`
is read-only, and `record_stop` finalizes the session. Repeating
`record_start` with the active label is the idempotent case described above;
using a different label returns `already_recording`. File listing, download,
deletion, and cancellation return `busy_recording`. Only one catalog or
download operation can be active at a time.

## File frames

`file_data` is a binary notification:

```text
uint32_le request_id
uint32_le offset
uint8[]   csv_bytes
```

The data portion is limited to `ATT payload - 8`. Android accepts only the
next contiguous offset. A wholly duplicated frame may be ignored. A gap,
overlap, buffer overflow, timeout, or disconnect interrupts the transfer and
leaves the contiguous `.part` file available for a later resume.

Android renames `.part` to the final CSV only after both byte count and CRC32
match `download_end`. A failed check never enables remote deletion. The local
partial file has sidecar metadata containing protocol version, device identity,
remote name, expected size, and CRC32.

## State and failure rules

- The board boots idle and never creates a dataset file without
  `record_start`.
- BLE disconnect does not stop recording. It cancels file operations and clears
  command/response fragments so a command from an old connection cannot run.
- Android treats collection state as unknown after disconnect and obtains
  `status` after reconnect.
- Active recording uses a temporary file. A complete CSV becomes visible only
  after all writes, sync, close, CRC metadata, and final rename succeed.
- Power loss or a write/sync/close failure leaves an incomplete file and moves
  recording to `fault`; incomplete files are never auto-downloaded or deleted.
- BLE remains unauthenticated for the laboratory prototype. Deletion still
  requires an exact managed name, size, CRC32, an idle logger, and explicit
  confirmation in Android.

## Timeouts

- Command response: 5 seconds.
- Catalog inactivity: 10 seconds.
- File data inactivity: 10 seconds.
- Android never blindly retries a mutating command after timeout. It sends
  `status` and reconciles the resulting state.
